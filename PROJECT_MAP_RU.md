## Приоритеты, основанные на коде

1. Windows-запуск: подтвердить, что SafeLaunch корректно открывает приложение при повторном запуске и конфликте 8080; проверить двойной клик и пути с пробелами/кириллицей. Текущий выбор свободного порта имеет окно гонки между проверкой и bind; подумать о повторе после BindException.
2. Локальная панель администратора: порт 8082 и ссылки на него заданы отдельно, часть ссылок возвращает на 8080. Выбор нового основного порта не исправляет автоматически эти ссылки. Нужны единый источник адресов и проверки конфликта admin-порта.
3. Подключение к уже работающему серверу: local == null, поэтому ZerdeDesktop25 не добавляет локальную admin-панель. Определить ожидаемое поведение и проверить сценарий явно.
4. Google setup/start в Server.java доверяют loopback remote address. Обратный туннель тоже приходит через loopback. Перед расширением внешнего доступа нужно пересмотреть эту границу доверия и добавить регрессионные тесты.
5. AdminConsole: отдельно проверить права, Host/Origin, изменение данных, первый setup, срок сессий и выход. Не считать local bind достаточной защитой сам по себе.
6. Восстановленные переменные var1/var2 и raw-типы: постепенно улучшать читаемость по модулям при зелёных тестах.
7. Database.java хранит доменные сущности в JSON. H2 использует MERGE/CLOB; PostgreSQL использует закрытую схему `zerdeai`, JSONB, `ON CONFLICT`, SSL `verify-full` и отдельную роль. При ошибке подключения H2 автоматически не выбирается.
8. Не помещать пароль PostgreSQL или service_role в web/app.js, общий ZIP или распространяемый exe. Для прямого JDBC доступ настраивается только на доверенном сервере. Если нужно раздавать приложение студентам, клиент должен работать через сервер API и пользовательскую авторизацию.

## Добавленные функции и ограничения

- H2 хранит `chats`, `chatMessages`, `courses`, `courseProgress`, `tutorDialogs` и `tutorMessages` в существующей таблице `records`. Старые резервные копии без этих категорий по-прежнему принимаются; при импорте проверяются участники диалога, владельцы курсов и ссылки прогресса.
- Чат разрешён студенту и преподавателю, связанному с его назначенной группой. Сервер проверяет участника каждого диалога; повтор с одинаковым `clientId` не дублирует сообщение.
- Курсы поддерживают тип, описание, разделы/уроки в JSON, публикацию, назначение группам и отметку выполнения урока. Загрузка видео, обложки/вложений, отдельное хранилище файлов, отдельное назначение ученику и редактор сортировки пока не реализованы.
- ИИ-тьютор использует AI-конфигурацию преподавателя студенческой группы, хранит собственные диалоги и не получает скрытые ответы, тесты или контекст экзамена. Сервер блокирует ряд прямых и разнесённых пробелами просьб о готовом ответе. Это дополнительная проверка, а не гарантия от всех вариантов обхода. История пользовательского текста передаётся выбранному преподавателем ИИ-провайдеру.
- Supabase Free project `zerdeai-shared` имеет приватную `zerdeai.records` с RLS. Java adapter и START_SUPABASE.ps1 добавлены, но runtime роль и пароль должен настроить владелец, а перенос текущей H2 и проверка записи/чтения из Java остаются незавершёнными. Пустая облачная база отклоняется при запуске.
- `scripts/build-installer.ps1` в обычном режиме собирает однофайловую оболочку через установленный .NET Framework C# compiler. `-UseIExpress` оставлен как альтернативный путь; IExpress в подготовительной среде не открыл RPT.

## Цель Supabase

Сначала определить режим: один доверенный сервер приложения и общая PostgreSQL-база либо перенос аутентификации/доступа на Supabase Auth. Сохранить H2 для офлайн-режима и совместимости. Для Supabase учитывать приватную схему, минимум прав, RLS в опубликованных схемах, SSL и хранение файлов отдельно от метаданных. При переносе H2 нужны dry-run, резервная копия, проверка связей и количества записей, затем проверка входа, назначений, попыток и оценок. Не включать одновременную запись в две базы без проработанных конфликтов.

Это список направлений проверки, а не завершённый аудит безопасности.
